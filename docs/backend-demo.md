## Step 3 — Persistence

**Migration version:** V1 (`V1__create_customer_interaction.sql`)
Creates `customer_interaction` table + supporting index. No prior migrations exist in this repo — this is the baseline schema for the Lab 49 slice.

**Primary key strategy:** UUID, generated by Hibernate (`@GeneratedValue(strategy = GenerationType.UUID)`), not app-assigned. Chosen over sequential/serial IDs to avoid exposing guessable identifiers and to keep interaction IDs distinct from human-readable customer fixture IDs (e.g. `CUS-1001`).

**Index purpose:** Composite index `idx_customer_interaction_customer_created` on `(customer_id, created_at DESC)`. Supports the timeline query `findByCustomerIdOrderByCreatedAtDesc` — both the filter (`customer_id`) and sort (`created_at DESC`) are covered by one index, avoiding a full table scan or separate sort step as timeline data grows. Verified via Hibernate SQL log (see below).

**Profile mapping:**
- Default profile → PostgreSQL (`jdbc:postgresql://localhost:5432/crm`). Not run/verified locally in Lab 49 — deferred to Lab 50 per project scoping ("Lab 50 builds UI and PostgreSQL proof on these contracts").
- `test` profile → H2 in-memory, `MODE=PostgreSQL` for closer dialect compatibility. Used for all repository test verification in this lab.

**Customer data ownership:** No `Customer` entity/table exists in this repo. `customer_id` is a plain indexed `VARCHAR`, no FK constraint — customer data is assumed owned by a separate bounded context/service, consistent with the starter's scope (Interaction slice only).

**Known type portability issue:** Initial migration used `TIMESTAMPTZ` (Postgres shorthand), which H2 rejected (`Unknown data type`). Resolved by using the full ANSI form `TIMESTAMP WITH TIME ZONE`, understood by both engines.

**SQL inspection (once, per instructions):**
```sql
select i1_0.id, i1_0.actor, i1_0.correlation_id, i1_0.created_at, i1_0.customer_id, i1_0.interaction_type, i1_0.summary
from customer_interaction i1_0
where i1_0.customer_id = ?
order by i1_0.created_at desc
```
Single query, no N+1 (no related-entity lazy loads present). Filter and sort both served by the composite index above.

**Seed data:** Amina (`CUS-1001`) and Ravi (`CUS-1002`) seeded via `@Sql("/seed-interactions.sql")`, test-scoped only (`src/test/resources`), fixed UUID fixture IDs to keep repository tests deterministic.

**Repository test:** `InteractionRepositoryTest.findByCustomerId_returnsAminaInteractionsOrderedByCreatedAtDesc` — passing, verifies save-and-query round trip against H2.


## Step 4 — Application service

**Transactional boundary:** `InteractionService.create()` is annotated `@Transactional`. Persistence (repository save) happens inside this boundary; event publishing does not — see below.

**Customer existence check:** No `Customer` entity/table exists in this repo (customer data is owned by a separate bounded context, out of scope for this slice). `requireCustomerExists(String customerId)` checks against a hardcoded fixture set (`CUS-1001`, `CUS-1002`) and throws `CustomerNotFoundException` for anything else, including `CUS-9999`.

**Actor:** No authentication exists yet in this repo (deferred to Lab 51). `actor` is currently a hardcoded placeholder (`"agent1"`) threaded through the mapper into the persisted row, satisfying the `nullable = false` constraint and CAP-12 criterion #5 (audit records actor) without a real identity source.
`// TODO: replace with real authenticated actor once Lab 51 auth exists`

**Correlation ID resolution:** `resolveCorrelationId` implements the required precedence: request header first, then the request body's `correlationId` field, then a fixed default (`"lab-request-001"`) if neither is present.

**Event publish timing — aligned with ADR-003:** The original Step 4 reference snippet published directly inside the `@Transactional` method, which would fire before the transaction actually commits — the exact failure mode ADR-003 warns against ("publish before persist without ADR"). Fixed via Spring's `@TransactionalEventListener`:

1. `create()` builds the event payload via `InteractionEventFactory`, then publishes a lightweight `InteractionRecordedApplicationEvent` wrapper through Spring's `ApplicationEventPublisher` — not the Kafka-bound publisher directly.
2. A separate `InteractionEventListener`, registered with `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`, only fires once the surrounding transaction has actually committed. That listener is what calls the real `InteractionEventPublisher.publish(...)`.

This guarantees no event is ever published for a row that failed to commit, matching ADR-003's core requirement without building the full transactional-outbox pattern the ADR explicitly deferred.

**Collaborators (constructor-injected, not static):**
- `InteractionRepository` — persistence
- `InteractionMapper` — request/entity/response conversion (`@Component` bean, not static, to allow future field/requirement changes without touching callers)
- `InteractionEventFactory` — builds `CustomerInteractionRecordedV1` from a saved entity (`@Component` bean, same reasoning)
- `ApplicationEventPublisher` — Spring's in-process event bus, used to defer the real Kafka-bound publish until after commit

**Tests (`InteractionServiceTest`):**
- `create_forAmina_returnsCreatedShape` — happy path, mocked collaborators, asserts response shape (id present, customerId/correlationId echoed correctly).
- `create_unknownCustomer_fails` — asserts `CUS-9999` throws, and explicitly verifies via `verify(..., never())` that neither `interactionRepository.save(...)` nor `applicationEventPublisher.publishEvent(...)` were called — proving the not-found path has no side effects, not just that an exception was thrown.

## Step 5 — REST endpoint

**Endpoints:**
- `POST /api/v1/interactions` — creates an interaction. Returns `201 Created` with the full `InteractionResponse` body on success.
- `GET /api/v1/customers/{customerId}/interactions` — returns that customer's interaction timeline, ordered most-recent-first (backed by `findByCustomerIdOrderByCreatedAtDesc`, built in Step 3). Path-based, not query-param based — chosen for REST resource-nesting clarity (interactions belong to a customer).

**Route structure note:** the two endpoints don't share a common path prefix (`/api/v1/interactions` vs `/api/v1/customers/{id}/interactions`), so `@RequestMapping` is not used at the class level — each method declares its full path individually via `@PostMapping`/`@GetMapping`.

**Correlation ID:** read from the optional `X-Correlation-ID` request header on POST, passed through to `InteractionService.create()`, which resolves final precedence (header > request body > `"lab-request-001"` default) as built in Step 4.

**Problem Details (RFC 7807):** implemented via a new `GlobalExceptionHandler` (`@RestControllerAdvice`), replacing Spring's default generic error handling:
- `CustomerNotFoundException` → `404`, detail message includes the offending customer ID.
- `MethodArgumentNotValidException` (Bean Validation failures on `@Valid` request bodies) → `400`, detail message aggregates all failing fields (`field: message`, semicolon-separated).

Both `getTimeline` and `create` reuse the same `CustomerNotFoundException` → 404 mapping, since both call `requireCustomerExists` internally.

**Security stub:** no Spring Security dependency exists in this repo yet (deferred to Lab 51). A `@PreAuthorize`-shaped TODO comment marks the intended enforcement point on `create()`, rather than adding a non-functional annotation without the supporting dependency.

**Known validation gap:** `interactionType` is currently only `@NotBlank` — it does not restrict values to the acceptance-criteria set (`CALL`/`EMAIL`/`NOTE`/`MEETING`). A `@Pattern` constraint would close this; not implemented in this pass, noted for follow-up.

**Tests (`InteractionControllerTest`, `@WebMvcTest`):**
- `create_forAmina_returns201` — happy path, mocked `InteractionService`, asserts status + key JSON fields via `jsonPath`.
- `create_invalidInteractionType_returns400` — empty `interactionType` triggers Bean Validation, asserts `400`.
- `create_unknownCustomer_returns404` — mocked service throws `CustomerNotFoundException`, asserts `404` via the global handler.

All three isolate the web layer only (`@WebMvcTest` + `@MockBean` on `InteractionService`) — no real service, repository, or database involved, consistent with the instructions' "without starting full server" intent from Step 4, now extended to the HTTP layer.

## Step 7 — Resilient consumer

**New table:** `audit_events` (migration `V2__create_audit_events.sql`). Primary key is `event_id` (supplied by the consumer from the Kafka event, not generated), serving double duty as both the audit trail and the dedup mechanism. No note/summary content is stored — only IDs, actor, correlation ID, and timestamps, consistent with "logs correlation without note body."

**Consumer:** `InteractionEventConsumer`, a `@KafkaListener` on `crm.customer.interactions.v1`, consumer group `audit-consumer`.

**Version validation:** rejects any event where `eventVersion` doesn't match `CustomerInteractionRecordedV1.VERSION`, throwing `IllegalArgumentException` — this is what triggers the retry/DLT pipeline below for incompatible events.

**Deduplication — corrected after an initial false pass:**
Initial implementation relied on catching `DataIntegrityViolationException` from a failed `INSERT`, assuming Spring Data JPA's `save()` would throw on a primary-key collision. Testing revealed this was incorrect: because `eventId` (the `@Id`) is always pre-assigned before `save()` is called, Spring Data JPA performs a `merge()` (SELECT + UPDATE) rather than a `persist()` (INSERT) — meaning a duplicate delivery silently **overwrote** the existing row instead of being rejected, and the catch block never fired. Fixed by explicitly checking `auditEventRepository.existsById(eventId)` before attempting any write, short-circuiting with a "Duplicate event ignored" log and no further DB activity on a repeat delivery. Verified via `InteractionEventConsumerTest#duplicateEvent_isNoOp`, confirming via SQL log that the second delivery triggers only a `SELECT`, no `INSERT`/`UPDATE`, and `audit_events` count stays at 1.

**Retry + DLT:** `DefaultErrorHandler` with `FixedBackOff(2000ms, 2 retries)` (3 total attempts) wraps a `DeadLetterPublishingRecoverer`, configured in `KafkaConsumerConfig`. On exhausted retries, the failed message is automatically republished to `crm.customer.interactions.v1.DLT`.

**Live end-to-end DLT verification (real Kafka, not mocked):**
1. App running on default profile, consumer subscribed and partition-assigned.
2. Console consumer attached to `crm.customer.interactions.v1.DLT`.
3. A message with `eventVersion: "99"` (unsupported) manually published to the main topic via console producer, keyed `CUS-1001`.
4. Message appeared on the DLT topic with key and full payload intact:

>CUS-1001 | {"eventId":"11111111-2222-3333-4444-555555555555", ..., "eventVersion":"99", ...}

Confirms the full pipeline: reject → bounded retries → exhausted → automatic DLT republish, with no manual intervention and no message loss.

**Observability:** structured logging at each decision point (`processed`, `duplicate ignored`, `version rejected`) with `eventId`/`correlationId`/`customerId`, satisfying the instructions' "counter or structured log" requirement via the log path. A metrics counter (Micrometer) was considered and deliberately deferred — logging was judged sufficient for this step's scope, and adding it would require a new dependency (`spring-boot-starter-actuator`) not otherwise needed.

**Tests (`InteractionEventConsumerTest`):**
- `duplicateEvent_isNoOp` — same event delivered twice; second call verified as inert (no exception, no row-count change).
- `incompatibleVersion_isRejected` — asserts `IllegalArgumentException` on unsupported version, the trigger for retry/DLT in real operation.

## Customer management slice (CAP-13 backend half)

**Why this exists:** the capstone brief lists customer management (create, update, search, lifecycle) as a required product capability, but neither Lab 49's nor Lab 50's written instructions assign it to any specific lab. It was identified mid-Lab-49 as a gap — frontend (CAP-13) needs it to build search/profile, and by process of elimination (not security's job, not explicitly frontend's job) it's backend work. Built as a second vertical slice, same rigor and pattern as the Interaction slice.

**Fields:** `customerId` (`CUS-XXXX`, server-generated, sequential), `fullName`, `status` (enum: `PROSPECT`/`ACTIVE`/`CLOSED`), `email`.

**Migration:**
- `V3__create_customer.sql` — creates `customer` table, seeds `CUS-1001` (Amina Khan, `ACTIVE`) and `CUS-1002` (Ravi Singh, `PROSPECT`), matching the capstone brief's fixture table exactly. Index on `full_name` supports partial-match search.
- `V4__add_customer_interaction_fk.sql` — adds the `customer_interaction.customer_id → customer.customer_id` foreign key that Step 3 (Lab 49) deliberately deferred, since no `customer` table existed at that time. Added as a separate migration, not retroactively edited into `V1`, since Flyway migrations are immutable once applied — this is the correct way to evolve a live schema.

**Sequential ID generation:** `CustomerRepository.findMaxCustomerIdNumber()` uses a JPQL query (`MAX(CAST(SUBSTRING(customer_id, 5) AS int))`) to find the highest existing numeric suffix; `CustomerService.generateNextCustomerId()` increments it. Defaults to `1000` (→ first ID `CUS-1001`) if the table is ever empty, though this path is untested in practice since fixtures are always seeded.

**Status lifecycle rules**, enforced via `CustomerService.LEGAL_TRANSITIONS`:
- `PROSPECT` → `ACTIVE` or `CLOSED` (legal)
- `ACTIVE` → `CLOSED` only (legal)
- `ACTIVE` → `PROSPECT` (illegal — no backward transition)
- Any status → itself (illegal — redundant, e.g. `ACTIVE` → `ACTIVE`)
- `CLOSED` → anything (illegal — terminal state)

Illegal/redundant transitions throw `IllegalStatusTransitionException` → `409 Conflict` via `GlobalExceptionHandler`, consistent with the existing `CustomerNotFoundException` → `404` pattern.

**Endpoints:**
- `POST /api/v1/customers` — create. Client supplies `fullName`/`email` only; server generates `customerId` and forces initial `status = PROSPECT` (no client override — onboarding always starts at prospect, matching the brief's described customer journey).
- `GET /api/v1/customers/{customerId}` — profile, exact ID lookup. `404` for unknown IDs (e.g. `CUS-9999`).
- `GET /api/v1/customers?query=...` — search. Tries exact-ID match first, falls back to case-insensitive partial name match (`"amina"` → Amina Khan).
- `PATCH /api/v1/customers/{customerId}/status` — lifecycle transition. Body: `{"newStatus": "ACTIVE"}`. Enum-typed field, so malformed values are rejected by Jackson before reaching application code.

**Closed the loop on a Step 4 TODO:** `InteractionService.requireCustomerExists` previously used a hardcoded `Set.of("CUS-1001", "CUS-1002")` as an explicit placeholder pending real customer data. Now replaced with `customerRepository.existsById(customerId)`, backed by the real `customer` table.
